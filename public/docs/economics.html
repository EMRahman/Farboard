Old ideas, new economics

Farboard's online play runs for free on Cloudflare, using ideas that are decades old. Cloudflare's scale made that possible, but understanding it was still the hurdle. AI got me over it: it found the option, built it with me, and explained it until I understood it.

The short version

Four steps took a familiar design to free

The design isn't new: one small server per game, holding both players' connections. Cloudflare made it free to run. AI made it possible for me to adopt it.

1 · Scale

Cloudflare can give this away because of how big it already is

Cloudflare already runs a global network for its CDN and DDoS protection. Workers run on capacity it had built anyway, so an extra small program costs it very little. Three design choices keep that cost tiny:

Isolates, not containers

Workers run in V8 isolates, the same sandbox a browser gives each tab. One starts in milliseconds and uses little memory, so a single machine can hold thousands of them. There's no virtual machine per customer to keep running.

Hibernation

A game's Room sleeps between moves while its WebSockets stay open at the edge. A chess game spends almost all of its time waiting for someone to think, so it costs almost nothing.

A free plan that stops, not bills

At its daily limit, the free plan pauses instead of charging. For Farboard, 100 games a day uses about 2% of the allowance (see the daily budget).

The free tier works like a funnel

Developers who start building on Cloudflare for free may later bring it paid work that would otherwise go to AWS. A generous free tier is how a smaller cloud competes with a bigger one.

2 · Packaging

Old ideas, packaged as one building block

None of the ideas behind a Durable Object are new. What Cloudflare did was package them together and make them cheap to run.

  • The actor model (1970s) and Erlang (1980s). Each piece of state lives in its own small process, and only that process can change it. One Room per game is exactly this, so there are no locks or database race conditions.
  • The stateful game server. It's what I'd have written on a VPS: one process holds both connections and forwards moves. A Room is that process, one per game.
  • Edge computing. CDNs have run on servers near users for decades, mostly to cache files. Workers let you run any code there.

AWS built serverless by combining separate services, each billed on its own. Cloudflare built a smaller set of building blocks around one cheap unit, the isolate, and gave state a home right next to it. On AWS the same relay needs API Gateway, Lambda, DynamoDB and IAM (compare the designs).

The hurdle

Cheap to run, but not cheap to understand

A free, well-packaged platform still costs something: the time to learn it. Durable Objects are a different mental model from a server you run yourself. To trust one with real players, I'd have had to read the docs, build a prototype, test how it behaves and design around what I found.

I've run VPS servers for 20 years. For a side project, that learning cost would have been bigger than anything the free tier could save, so the sensible choice was the server I already knew. The economics of the platform had changed, but the economics of learning it hadn't.

3 · Discovery

AI showed me the option existed

I didn't know this design existed until an AI coding assistant suggested it, together with a VPS relay, AWS serverless and WebRTC peer-to-peer. Twenty years of good habits meant I'd never gone looking. You can't weigh an option you don't know about.

The AI also said what each option would cost to run and where it would struggle. For example, WebRTC can't always connect phones directly on mobile and office networks, so it still needs a relay. Design alternatives compares all four.

4 · Understanding

AI built it, then explained it, to avoid cognitive debt

The AI built a working version quickly. That made trying the unfamiliar design cheap: I compared real, working code instead of guessing.

Speed brings a risk. Cognitive debt, also called comprehension debt, is what builds up when code ships that nobody understands. Like technical debt, you pay it back later, usually during an outage, when no one can say how the system works (Margaret-Anne Storey, Addy Osmani).

So the other half of the work was paying that debt down as it was taken on:

  • Explained back to me. I learned Durable Objects well enough to judge for myself that this design is simpler. I'm not taking the AI's word for it.
  • Written down. The explanations became this site's guides: Architecture (what it's made of and why), Implementation (how it's coded, message by message) and Design alternatives (what else was considered).
  • Kept small. The whole relay is one Worker and two classes, so it's still small enough to hold in one person's head.

What AI did: it lowered the cost of exploring, building and learning. What it didn't do: make the choice. I chose Cloudflare after comparing working versions and understanding them.

The wider conversation

Where this fits in how people talk about AI

Cheaper code means more gets built

The Jevons paradox: when something gets cheaper, people use more of it. Applied to AI, ideas that weren't worth building before now clear the bar (Jim Montgomery). Here, it wasn't a feature that became worth building. It was a whole architecture that became worth trying.

"Choose boring technology," revisited

The classic advice is to stick with proven tools, and some argue AI makes that more important, because you can't check an AI on technology you don't know (Aaron Brethorst; compare Simon Willison). My answer is in between: new technology is fine if the AI teaches it to you well enough to check.

Home-cooked software

Small apps built for friends and communities, not for scale (Maggie Appleton). Free tiers are what keep them running for years, and Farboard's Deploy to Cloudflare button lets anyone run their own copy at no cost.

Durable Objects for AI agents

Cloudflare builds its Agents SDK on Durable Objects: one actor per agent, using no compute while it's asleep. It's the same property that makes one Room per chess game free, which suggests the design will be supported for a long time.

Caveats

What I'm keeping an eye on

  • Building it isn't running it. I haven't had a production incident on Cloudflare yet, so I'm practising now, while nothing is broken: reading Workers Logs, checking a Room's state and the request counts, and rolling back a deploy.
  • Lock-in is real but small. Durable Objects exist only on Cloudflare. Leaving would mean redesigning the relay (relay/src/room.js), and nothing else. The VPS design is still a working way out.
  • Free tiers can change. If the free plan changed, the fallback is the same small design on a paid plan or on a VPS.
